# 予約起点の来店登録を状態遷移APIへ統一（2026-10-26）

## 利用者ができること

予約一覧またはスタッフホームの「来店登録へ」から、予約と来店履歴を紐付けて登録できる。旧共有ログインでも、表示時点の予約状態が変わっていないことを確認してから登録し、保存後に予約を完了へ進める。

## 今回の変更

- 予約一覧とスタッフホームから、予約IDに加えて表示時点の生の予約状態を来店登録画面へ渡す。
- 予約起点の来店登録では顧客選択を固定し、予約の顧客IDと送信された顧客IDをサーバーで照合する。
- 旧共有ログインでは、来店履歴を書き込む前に認証済み予約状態APIで `表示時点の状態 -> 来店` を実行する。
- 来店履歴に `reservation_id` を保存し、同じ予約に紐付く来店履歴が既にある場合は再登録を拒否する。
- 来店履歴と後続処理の保存後、同じAPIで `来店 -> 完了` を実行する。
- 古いURLなどで表示時点の予約状態がない場合は、書込み前に予約一覧の再読込を案内する。
- 個別スタッフ認証の `register_staff_visit` RPC経路は変更しない。

## 確認したこと

- 旧共有ログインで `来店状態更新 -> 予約ID付き来店保存 -> 完了状態更新` の順に処理される。
- 予約状態の欠落、状態変更、取消・完了済み、既存の紐付き来店履歴で、来店保存前に停止する。
- 別顧客へ差し替えたURLや古い画面では、予約状態を変更せず来店保存前に停止する。
- 状態を `来店` へ進めた直後に来店保存が失敗した場合は、同じ顧客・予約で来店履歴が未作成の時だけ再開できる。
- 来店済み状態からの再開と表記ゆれを扱える。
- 個別スタッフ認証は引き続き直接テーブルを書かず、既存の原子的APIを使う。

## 導入条件と未検証範囲

コード変更に新しいmigration、環境変数、外部送信は不要。Previewでの画面確認と実DBでの予約・来店履歴の保存確認は未実施。本番反映も未実施。旧共有ログインの保存は複数テーブルにまたがる既存の非原子的経路であり、今回の事前状態比較と既存履歴確認で通常の再送を拒否するが、別端末から同時に操作した場合の完全な一意性はDB制約なしでは保証しない。

## Preview受入手順

1. 予約一覧またはスタッフホームで、テスト予約の「来店登録へ」を開く。
2. 会計内容を入力して1回だけ登録する。
3. 顧客詳細で来店履歴が1件表示され、予約一覧で予約が完了になることを確認する。
4. 同じ予約の古い画面から再登録し、既存履歴または状態変更の案内で停止することを確認する。

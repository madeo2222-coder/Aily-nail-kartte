# Gmail予約登録とキャンセルの逆順競合（2026-10-22）

## 利用者への効果

Gmail予約登録とキャンセル同期がほぼ同時に動いた場合でも、遅れて完了した予約登録によってキャンセル済み予約が復活しないようにする。

## 原因

予約登録は事前に既存予約を確認した後、決定的IDで`UPSERT`していた。確認直後に別処理が同じIDのキャンセル行を作ると、予約側の遅い`UPSERT`がその行を`confirmed`で上書きできた。

## 変更範囲

- 新規予約の保存を`UPSERT`から`INSERT`へ変更し、同じIDの競合を一意制約エラーとして検知する。
- 競合時は同じIDを1回再読取する。
- 同一サロンのキャンセル済み行なら、その状態を維持して成功へ収束する。
- 同一サロンの通常予約なら、既存のサロンID付き更新経路へ切り替える。
- スタッフが「来店」「完了」などへ進めた行は、その状態とメモを保持する。
- 別サロンまたは所属不明、再読取失敗、一意制約以外のDBエラーは成功扱いしない。

DB schema、migration、Supabase設定、認証、環境変数、実Gmail・LINE送信は変更しない。

## 受入条件

1. キャンセル行の作成後に予約登録が遅れても、キャンセル状態が維持される。
2. 同時作成された通常予約は重複させず、同じ行へ収束する。
3. スタッフ進行状態とメモを上書きしない。
4. 別サロンの行を更新しない。
5. 保存結果不一致や通常のDBエラーを成功扱いしない。

## 既存予約UPDATE競合の追加保護

上記は新規INSERTが同時になった場合を保護する。既存予約では、予約受付メール側が`confirmed`を読んだ直後に別実行がキャンセルを保存すると、遅いUPDATEがキャンセルを上書きする余地が残っていた。

- 既存予約UPDATEに読取時点の`status`を条件として追加する。
- 条件不一致時は最新行を読み直し、キャンセル済みなら追加UPDATEせず`cancelled / alreadyCancelled`へ収束する。
- キャンセル以外へ同時変更された場合も古い状態で上書きせず、最新状態を確認して再試行するよう失敗を返す。
- INSERT競合後のUPDATEにも同じ状態条件を適用する。
- 模擬DBで`confirmed`読取後にキャンセルが確定する順序を再現し、予約受付メール側の追加UPDATEが行われないことを確認する。
- 追加後の対象74件、全回帰746件中744件成功・失敗0・任意PGlite 2件skip。型検査、lint、fixture環境のNext.js production build（93画面）も成功した。

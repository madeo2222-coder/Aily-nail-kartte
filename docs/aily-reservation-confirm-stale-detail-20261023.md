# 予約確定時の古い編集内容による上書き防止

## 利用者が新しくできること

スタッフが予約編集画面を開いた後、Gmail同期や別端末の操作で予約内容が更新されていても、古い画面の内容でそのまま予約確定して変更を巻き戻さなくなった。

更新を検知した場合は確定処理を止め、「最新の内容を読み込み直してください」と案内する。画面を再読み込みし、最新の顧客・担当者・メニュー・日時・状態・メモを確認してから確定する。

## 今回の変更

- 予約編集画面から確定APIへ、画面表示時点の顧客・担当者・メニュー・開始日時・終了日時・状態・メモを送る。
- 確定APIは現在の予約と画面表示時点の値を比較し、1項目でも変わっていれば `409 Conflict` で確定を拒否する。
- 予約一覧からの確定は編集値を送らない既存動作を維持する。
- 既存の `confirm_staff_reservation` RPCによる状態・日時の再確認、時間帯重複拒否、確定済み予約の再通知防止を維持する。

## 検証範囲

- 元データ7項目が欠けた編集確定を拒否すること。
- 顧客・担当者・メニュー・開始日時・終了日時・状態・メモの各項目について、取得後の変更を検知してRPCを呼ばないこと。
- 予約一覧の空JSONによる確定、所属店舗制限、過去時刻拒否、重複拒否、確定済み予約の再通知防止が維持されること。

## 未検証・制約

- 本番DBの実データや実LINE送信は使用していない。
- APIが予約を読み取った直後からRPC実行までの極短い間に、日時以外の項目だけが別処理で変更された場合の完全な原子性は、現在のRPC引数では保証できない。完全な保証には既存関数のDB変更が必要なため、今回のDB変更なしの納品範囲には含めない。
- Preview反映後も、認証済みスタッフによる実接続の入力→確定→再表示は別途確認する。

## 変更しないもの

- Supabase migration、RLS、権限、環境変数
- 実顧客へのLINE・メール送信
- mainおよび本番公開

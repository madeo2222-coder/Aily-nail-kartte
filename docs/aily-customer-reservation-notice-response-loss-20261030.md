# 顧客予約申請の応答喪失後通知再試行（2026-10-30）

## 利用者が新しくできること

顧客が予約申請を送った直後に通信が切れ、結果不明画面から同じ申請を再試行した場合、保存済みの自分の予約を重複枠として扱わず、同じ予約へ収束できる。

保存後に店舗向け通知処理が中断していた場合も、同じ申請IDでメール・LINE通知を安全に補完する。既に各配信事業者が受け付けていた場合は、同じ冪等キーを再利用して重複送信を防ぐ。

## 変更範囲

- 顧客予約申請の空き枠再確認では、ブラウザの操作IDと同じ予約IDを除外する。
- Resendメールは予約ID由来の `Idempotency-Key` を使用する。
- 店舗向けLINEは予約ID由来のUUID v4形式 `X-Line-Retry-Key` を使用する。
- RPCが `already_created` を返した場合も通知処理を同じキーで再試行する。
- 新規DB変更、権限変更、env変更、実メール・実LINE送信は行わない。

## 受入条件

1. 同じ操作IDの再試行が、自分の保存済み予約との重複判定で止まらない。
2. 初回と再試行でメール・LINEの冪等キーが同一になる。
3. 異なる内容で同じ操作IDを使った場合は既存RPCの競合判定を維持する。
4. RPC未適用の実DBでは従来の後方互換経路を維持し、適用済みとは扱わない。

## 未検証範囲

- Aily実DBでの操作ID RPC適用状況と保存・再表示
- 通常顧客LINE認証を使った実環境操作
- Resend・LINEの実配信
- 別端末での同時申請

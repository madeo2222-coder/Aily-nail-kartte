# 予約キャンセル時の古い画面による上書き防止

## 利用者に変わること

スタッフが予約編集画面を開いた後、Gmail同期や別端末の操作で予約内容が変わっていた場合、古い画面からその予約をキャンセルしなくなった。

競合を検知した場合はキャンセル更新とLINE送信を止め、「最新の内容を読み込み直してください」と案内する。再読込後、最新の担当者・日時・状態・メモ等を確認してから操作する。

## 実装範囲

- 予約編集画面からキャンセルAPIへ、画面読込時点の顧客・担当者・メニュー・開始/終了日時・状態・メモを送る。
- APIは現在の予約内容と画面読込時点の内容を比較し、差分があれば `409 Conflict` で拒否する。
- 読取後からUPDATE実行までに予約内容が変わった場合も、各項目を更新条件へ含めて競合として扱う。
- DB上の未設定値は `IS NULL` 条件で比較する。
- 既にキャンセル済みの場合は従来どおり成功扱いに収束し、LINEを再送しない。
- 個別スタッフの所属サロン制限、キャンセルLINEの送信結果区分、ブラウザ連打防止を維持する。

## 受入条件

1. 画面表示後に同期または別端末で担当者、日時、状態、メモ等が変わった場合、古い画面からキャンセルされない。
2. 競合時はLINEを送らず、最新内容の再読込を案内する。
3. 競合がない場合は従来どおりキャンセルし、希望時だけLINE送信を試みる。
4. 別操作で既にキャンセル済みの場合は成功に収束し、LINEを再送しない。

## 検証

- 予約キャンセル関連テスト: 10件成功
- 全回帰: 801件中799件成功、失敗0、任意PGlite 2件スキップ
- TypeScript型検査、変更ファイルlint成功

## 未検証・変更していない範囲

- Aily実DB、実Gmail、実スタッフ認証を使った同時更新
- 実LINE送信
- Supabase migration、RLS、権限、環境変数
- main、本番環境

本変更は既存の予約列を比較条件に使うため、DB schemaの変更は不要。

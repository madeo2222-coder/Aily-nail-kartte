# 予約確定メールのブラウザ応答喪失対策（2026-10-30）

| 項目 | 内容 |
| --- | --- |
| 利用者・目的 | スタッフが予約確定メールを送った直後に通信が切れたりブラウザが応答を受け取れなかった場合も、再読込後の再試行で顧客へ同じメールを重複送信しない |
| 納品範囲 | 予約一覧・予約編集の初回メール送信前に一度限りの要求IDを固定し、再試行情報と一緒に24時間だけ保存する。メールAPIは同じ要求IDを同じResend冪等キーへ変換する |
| 受入条件 | 初回応答が失われても同じ予約の再試行が同じprovider keyを使う。サーバー応答を受け取った失敗では送信先・予約内容が変わった再試行を409で拒否する。期限切れ・正常完了後は再試行情報を削除する |
| 残件 | Aily実環境の通常スタッフ認証、実メール送信履歴、別端末同時操作での確認 |
| 予定 | 次回の単一Preview候補。Vercel誘発操作は最新試行から6時間以上空け、他の検証済み成果とまとめる |
| 必要な本人操作 | 現時点なし。実メール受入を行う段階で、送信先を確定したテスト予約が必要 |

## 実装

- ブラウザで予約確定メール送信を始める直前にUUID v4の要求IDを生成する。
- 予約ごとの再試行情報へ要求IDを保存し、再読込後の再試行でも同じIDを使う。
- サーバーは予約IDと要求IDからResendのprovider keyを生成する。同じブラウザ送信試行は予約内容が途中で変わっても同じprovider keyへ収束する。
- サーバーが返したpayload検証キーは別に維持し、応答を受け取れた一時失敗後に予約内容・送信先が変わった場合はResendを呼ぶ前に拒否する。
- 要求IDは形式検証し、不正な値では管理クライアントやResendを作成しない。旧画面から要求IDなしで呼ばれた場合は従来のpayload由来キーを維持する。

## 検証範囲

- 不正な要求IDの400拒否
- 同じ要求IDを使った再試行のprovider key一致
- payloadが変わっても、ブラウザ応答喪失後の再試行が同じprovider keyを使うこと
- サーバー応答を受け取った失敗では、payload変更時に409で停止すること
- 要求IDのlocalStorage保存・再読込復元・期限維持
- 予約一覧と予約編集の両画面が初回生成と再試行再利用を行うこと

Aily実DB、実顧客メール、実LINE、実機、本番は変更・検証していない。DB migration、RLS、環境変数、依存パッケージの変更はない。

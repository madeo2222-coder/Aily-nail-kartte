# 別日時依頼LINEの古い画面対策（2026-10-23）

## 利用者が新しく安全にできること

スタッフが予約編集画面から「別の希望日時を入力してもらう」を実行するとき、画面を開いた後に別端末や予約同期で予約内容が変わっていた場合は、LINEを送らずに最新内容の再読込を案内する。

これにより、スタッフが見ていない変更後の顧客・予約日時を使って「この日時では確定できない」というLINEを送る事故を防ぐ。

## 実装範囲

- 画面表示時の顧客、担当、メニュー、開始・終了日時、状態、メモをAPIへ送る。
- APIは現在の予約と全項目を比較し、差があれば `409` で停止する。
- スナップショットが欠けた古い画面・不正な要求は `400` で停止する。
- 日時は保存表現が異なっても同一時刻なら一致として扱う。
- 不一致時は送信台帳のclaimもLINE API呼出しも行わない。

## 検証

- 必須スナップショット欠落・型不正の拒否
- 顧客、担当、メニュー、開始・終了日時、状態、メモそれぞれの古い値を拒否
- 拒否時にclaim・LINE送信・完了記録が発生しないこと
- 正常送信、送信済み収束、LINE失敗・再試行、結果不明時の再送防止の既存回帰
- 画面が7項目を送信すること

## 未検証・導入条件

- Aily実DB、実スタッフ認証、実顧客LINEでは未検証。
- DB migration、環境変数変更、実送信は行っていない。
- 既存のDB claim関数による状態・顧客・サロンのロックは維持する。APIの読取照合からDB claim取得までの極小の同時更新窓を完全に原子化するには、既存関数の実DB適用状況を確認した後に、期待値を関数へ渡すDB変更を別途検討する。今回の変更は、通常の古い画面操作をDB変更なしで先に防ぐ範囲である。
- Preview READYだけで現場試用完了とは扱わない。通常のスタッフ認証で、古い画面の送信拒否と最新画面の送信前状態までを確認し、実送信は許可されたテスト顧客に限定する。

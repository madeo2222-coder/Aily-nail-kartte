# 予約一覧からの古い内容による確定防止

## 利用者が新しくできること

スタッフが予約一覧を開いた後、Gmail同期や別端末の操作で顧客・担当者・メニュー・日時・状態・メモが変わっていても、古い一覧表示のまま予約を確定しなくなった。

更新を検知した場合は確定とLINE送信を止め、「最新の内容を読み込み直してください」と案内する。再読み込み後に最新内容を確認してから確定する。

## 今回の変更

- 予約一覧から確定APIへ、一覧表示時点の顧客・担当者・メニュー・開始日時・終了日時・状態・メモを送る。
- 確定APIは現在の予約と一覧表示時点の値を比較し、1項目でも変わっていれば `409 Conflict` で確定を拒否する。
- 一部だけの不完全なスナップショットは確定前に拒否する。
- 更新前クライアントからの空JSONは互換性のため維持し、既存のRPCによる状態・日時・重複の最終確認を継続する。
- `docs/aily-reservation-confirm-stale-detail-20261023.md` に記録した「予約一覧は編集値を送らない」という旧範囲は、この変更により一覧にも拡張された。

## 検証範囲

- 一覧が7項目すべての表示時スナップショットを送ること。
- スナップショットが1項目でも欠ける場合はRPCを呼ばないこと。
- 顧客・担当者・メニュー・開始日時・終了日時・状態・メモの各変更を検知し、確定とLINE送信に進まないこと。
- 更新前クライアントの空JSON、編集画面からの確定、所属店舗制限、過去時刻拒否、重複拒否、確定済み予約の再通知防止が維持されること。

## 未検証・制約

- 本番DBの実データや実LINE送信は使用していない。
- APIが予約を読み取った直後からRPC実行までの極短い間に、日時以外の項目だけが別処理で変更された場合の完全な原子性は、現在のRPC引数では保証できない。完全な保証には既存関数のDB変更が必要なため、今回のDB変更なしの納品範囲には含めない。
- Preview反映後も、認証済みスタッフによる実接続の一覧表示→確定→再表示は別途確認する。

## 変更しないもの

- Supabase migration、RLS、権限、環境変数
- 実顧客へのLINE・メール送信
- mainおよび本番公開

# 予約一覧の古い状態による上書き防止

## 利用者に変わること

スタッフが予約一覧を開いた後、Gmail同期や別端末の操作で予約状態が変わっていた場合、古い一覧から「来店」または「完了」に上書きしなくなった。

競合を検知した場合は更新を止め、「最新の内容を読み込み直してください」と案内する。再読込後、最新状態を確認してから操作する。

## 実装範囲

- 予約一覧から状態更新APIへ、一覧表示時点のDB上の状態を送る。
- APIは所属サロン内の現在状態と表示時点の状態を比較し、差分があれば `409 Conflict` で拒否する。
- 読取後からUPDATE実行までに状態が変わった場合も、表示時点の状態を更新条件へ含めて競合として扱う。
- DB上の状態が未設定の場合は `IS NULL` 条件で保護する。
- 個別スタッフの所属サロン制限と署名済み共有ログインの既存経路を維持する。

## 受入条件

1. 一覧表示後に予約がキャンセルまたは別状態へ変更された場合、古い一覧から「来店」「完了」に変更されない。
2. 競合時は最新内容の再読込を案内し、更新成功として表示しない。
3. 競合がない場合は従来どおり状態を更新し、一覧を再取得する。
4. 存在しない予約は従来どおり404として扱う。

## 未検証・変更していない範囲

- Aily実DB、実Gmail、実スタッフ認証を使った同時更新
- Supabase migration、RLS、権限、環境変数
- 実LINE・メール送信、main、本番環境

本変更は既存の `reservations.status` による比較更新であり、DB schemaの変更は不要。

# 予約キャンセル競合時の誤成功防止

## 1. 利用者が新しくできること

スタッフが予約をキャンセルする直前に別端末・別操作で予約状態が変わっても、実際にはキャンセルされていない予約を「キャンセル成功」と表示しません。予約が別の状態へ進んでいた場合は再読み込みを案内し、実DBと画面表示の食い違いを防ぎます。

## 2. 操作手順

通常どおり予約編集画面からキャンセルします。競合がなければ従来どおり保存されます。同時更新があった場合は、表示された案内に従って画面を再読み込みし、最新状態を確認します。

## 3. 実際に確認した業務

- 読取後から更新までに予約が「来店」へ変わった場合、HTTP 409 と `reservation_changed` を返し、キャンセル成功にしない。
- 別操作で既にキャンセル済みになった場合だけ、冪等な成功として扱いLINEを再送しない。
- 競合後の再読取に失敗した場合、成功にせず再読み込みを案内する。
- 競合中に予約が削除された場合、404として成功にしない。
- いずれの競合経路でもLINE送信を開始しない。

## 4. 今回の範囲と未検証

本変更はAPIの競合判定と回帰テストだけです。DB、migration、認証設定、LINE設定は変更していません。実DBの同時更新、実スタッフ認証、実LINE送信、Preview、本番では未検証です。

LINE送信失敗後の安全な再試行には、取消し通知専用の永続送信台帳と同一リトライキーが必要です。現状は送信結果が不明なまま重複送信する方が危険なため、この変更では再送機能を追加していません。DB適用案を準備・検証し、必要時に対象プロジェクト `shnkwaunrycqxgboqnam` へユーザーが手動適用する既存方針を維持します。

## 5. 受入条件

- 通常のキャンセルが従来どおり保存される。
- 同じ予約を別端末で先に「来店」などへ変更した後、古い画面からキャンセルしても成功表示にならない。
- 最新状態を再読み込み後、実DBと画面の状態が一致する。
- 同時にキャンセルした場合、二重更新・LINE二重送信が起きない。

## 6. 次の納品工程

検証済み成果を次の単一Previewバッチ候補として保持します。Preview反映後、許可されたテスト予約で二つの画面を使い、片方で状態更新、もう片方でキャンセル、再読み込み後の状態一致まで確認します。取消しLINEの再試行は、専用送信台帳の読取確認・適用案・承認条件を切り分けて進めます。

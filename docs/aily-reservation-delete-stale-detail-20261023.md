# 予約削除時の古い画面による誤削除防止

## 利用者に変わること

スタッフが予約編集画面を開いた後、Gmail同期や別端末の操作で予約内容が更新されていた場合、古い画面から最新予約を削除しなくなった。

更新を検知した場合は削除を止め、「最新の内容を読み込み直してください」と案内する。画面を再読み込みし、最新の顧客・担当者・メニュー・日時・状態・メモを確認してから削除する。

## 実装範囲

- 予約編集画面から削除APIへ、画面表示時点の顧客・担当者・メニュー・開始日時・終了日時・状態・メモを送る。
- 削除APIは現在の予約と画面表示時点の値を比較し、変更があれば `409 Conflict` で削除を拒否する。
- 読取後からDELETE実行までに変更された場合も、同じ値を削除条件へ含めて削除対象を0件にし、競合として扱う。
- 個別スタッフの所属サロン制限と署名済み共有ログインの既存経路を維持する。

## 受入条件

1. 予約を開いた後にGmail同期または別端末で内容が変わった場合、古い画面から削除されない。
2. 競合時は最新内容の再読込を案内し、削除成功として表示しない。
3. 競合がない予約は従来どおり削除できる。
4. ブラウザの連打防止と結果不明時の再操作停止を維持する。

## 未検証・変更していない範囲

- Aily実DB、実Gmail、実スタッフ認証による同時更新
- Supabase migration、RLS、権限、環境変数
- 実LINE・メール送信、main、本番環境

本変更は既存列による比較削除であり、DB schemaの変更は不要。

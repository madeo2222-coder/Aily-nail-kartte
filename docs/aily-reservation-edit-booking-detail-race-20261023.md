# 予約編集と同期の競合保護（2026-10-23）

## 利用者が新しくできること

スタッフが予約編集画面を開いた後にGmail予約同期が顧客、担当スタッフ、またはメニューを更新しても、古い画面から保存して同期結果を元に戻すことがなくなる。競合時は保存せず、最新内容の読み直しを案内する。

## 今回の納品単位

- 予約編集画面の取得時点で、顧客ID、担当スタッフID、メニューの元の値を保持する。
- 保存時に元の値をAPIへ送り、サーバーで現在値との一致を確認する。
- 読取後から書込みまでの間に同期が走った場合にも、同じ値を更新条件へ加えて競合を拒否する。
- 元の値が未設定の場合は、DB上でも未設定のままであることを条件にする。

## 受入条件

1. 画面表示後に同期が顧客IDを変更した場合、古い画面の保存は409で拒否され、予約は変更されない。
2. 担当スタッフまたはメニューが同期で変更された場合も同様に拒否される。
3. 同期変更がない通常の予約編集はこれまでどおり保存できる。
4. 顧客、担当スタッフ、メニューが元から未設定の予約も安全に保存できる。

## 検証範囲

- API認証・所属制限を維持した対象テスト
- 顧客、担当スタッフ、メニューそれぞれの競合拒否
- DB書込み直前の競合拒否
- 未設定値の `IS NULL` 条件
- 全回帰テスト、型検査、lint、ローカルproduction build

## 未検証・未変更

- Aily実DBでの書込み、実顧客データ、実LINE／メール送信は実施していない。
- DB migration、Supabase設定、環境変数、本番mainは変更していない。
- Previewへの反映は6時間間隔を守り、次の統合バッチで行う。

## 操作手順

Preview反映後は通常のスタッフ認証で予約編集画面を開き、顧客・担当・メニュー・日時などを編集して保存する。別経路で予約内容が更新済みの場合は表示された案内に従って画面を読み直す。
